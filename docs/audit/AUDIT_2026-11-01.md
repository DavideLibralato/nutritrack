chiave segreta nel client, calcolo del giorno e calcoli nutrizionali corretti

- **Fuori perimetro** (§9.5): social (con l'eccezione Amici), gamification,

## Segnalazioni

### [CRITICO] #1 — Una modifica fatta durante l'invio della stessa riga non arriva mai al server

- **Tipo:** Bug (race condition)
- **Dove:** `src/lib/sync/sincronizza.ts:249`
- **Cosa succede:** il giro di salita legge la coda, manda la voce e, se il
  server risponde ok, la cancella **senza controllare** che sia ancora quella
  inviata:

  ```ts
  const risposta = await conTempoMassimo(supabase.from(voce.tabella).upsert(voce.dati));
  // ... intanto l'utente può riscrivere la stessa riga ...
  inviate += 1;
  await db.outbox.delete(voce.id);   // id = "<tabella>:<id riga>"
  ```

  L'id della voce in coda è `"<tabella>:<id riga>"` (`outbox.ts:111`), quindi
  una seconda scrittura della stessa riga **sovrascrive** la voce in coda.
  Se arriva mentre l'`upsert` della prima è in viaggio, la `delete` finale
  toglie dalla coda la **seconda** versione, che il server non ha mai visto.
  Il giro prenotato dopo trova la coda vuota.

  Il caso più probabile è proprio quello che §10.2 incoraggia: tocco "+",
  poi "Annulla" entro un paio di secondi. `annullaOperazione`
  (`vociDiario.ts:117`) chiama `repositoryVociDiario.elimina(id)`, che scrive
  `deleted_at` sulla stessa riga e la riaccoda con lo stesso id. Con una rete
  mobile lenta l'inserimento è ancora in viaggio.

  Risultato: sul telefono la voce è annullata, sul server è viva.
  - Sugli altri dispositivi la voce c'è.
  - Dopo "Esci" (che controlla solo che la coda sia vuota, e lo è) o un
    ripristino, la voce annullata **ricompare** nel diario e nei totali.
  - Se il `updated_at` scritto dal server (ora di arrivo del primo invio) è
    più recente di quello locale dell'Annulla, la discesa successiva la
    rimette viva anche su questo telefono (`discesa.ts:357`).

  Nessun test lo copre: `sincronizzaUnaPerVolta.test.ts` prova solo righe
  **diverse** accodate durante un giro (m1, m2), mai la stessa riga riscritta.

  Lo stesso difetto, più piccolo, c'è sui rami di errore (`db.outbox.update(voce.id, …)`
  alle righe 211, 225, 242): tentativi e accantonamento finiscono sulla voce
  nuova, che non è mai stata provata.
- **In parole semplici:** è come un job batch che legge un record da una
  coda dati, lo elabora e poi fa `DELETE` del record per chiave, senza
  controllare che nel frattempo un altro programma non l'abbia riscritto con
  dati nuovi. Su AS400 lo bloccheresti con un lock o un confronto del
  timestamp di modifica. Qui manca quel confronto.
- **Perché conta:** è la trappola n. 1 di §10.6 ("l'annulla deve annullare
  anche la sincronizzazione"). Non fa rumore: niente errori, nessuna voce
  accantonata, l'indicatore dice "tutto sincronizzato". Le calorie di un
  giorno risultano sbagliate e lo scopri dopo, su un altro dispositivo o al
  rientro.
- **Come sistemarlo:** cancellare (o aggiornare) la voce solo se è ancora
  quella inviata, in una transazione Dexie:

  ```ts
  await db.transaction("rw", db.outbox, async () => {
    const attuale = await db.outbox.get(voce.id);
    if (attuale && attuale.creato_il === voce.creato_il) {
      await db.outbox.delete(voce.id);
    }
    // altrimenti: è arrivata una versione nuova, resta in coda per il giro prenotato
  });
  ```

  `creato_il` ha la risoluzione del millisecondo: due scritture della stessa
  riga nello stesso millisecondo restano possibili. Una soluzione più solida
  è un campo `rev` (un uuid nuovo a ogni `accodaMutazione`). Cambia la forma
  delle righe di `outbox`, quindi serve `this.version(10)` (regola B di
  `CLAUDE.md`). La voce resta valida senza `.upgrade()` se il codice tratta
  `rev` assente come "non confrontabile, cancella come oggi".

  Test permanente (è una race condition, sezione test di `CLAUDE.md`): server
  finto con `upsert` lento come in `sincronizzaUnaPerVolta.test.ts`. Si accoda
  la riga v1, parte il giro, si riaccoda la stessa riga con `deleted_at`
  durante l'attesa. Alla fine il server deve aver ricevuto anche la versione
  con `deleted_at`.
- **Impegno stimato:** piccolo (correzione + test), medio con il campo `rev`.

### [ALTO] #2 — Next.js 16.3.3 con vulnerabilità note (npm audit: critica)

- **Tipo:** Rischio (sicurezza)
- **Dove:** `package.json` (`"next": "16.3.3"`, `eslint-config-next 16.3.0`);
  dipendenze indirette `sharp 0.35.4`, `source-map-js`
- **Cosa succede:** `npm audit --omit=dev` elenca 11 avvisi su
  `next 16.0.0 – 16.4.0`, fra cui due RCE (Image Optimization con SVG, `use
  cache`), un DoS con le Server Actions e un SSRF in Image Optimization.
  Corretti in `next@16.4.3`. `sharp < 0.35.5` (alta) e `source-map-js` (alta)
  si sistemano con `npm audit fix`.
- **Quanto ti tocca davvero:** l'app non usa `next/image`, `use cache` né
  `ImageResponse`. Usa però una Server Action (`registrati`), e l'endpoint
  `/_next/image` esiste comunque. Non ho provato a sfruttarli: "da aggiornare
  comunque" più che "sfruttabile oggi".
- **In parole semplici:** è come restare indietro con le PTF di sistema: oggi
  forse nessuno entra da lì, ma le patch sono pubbliche, e lo è anche come
  sfruttare chi non le ha messe.
- **Perché conta:** l'app è pubblica su `app-libra.vercel.app` con dati
  sanitari di persone reali.
- **Come sistemarlo:**
  ```
  npm install next@16.4.3 eslint-config-next@16.4.3
  npm audit fix
  npm run build
  npx vitest run
  ```
  Poi prova su anteprima Vercel prima del merge, come da abitudine.
- **Impegno stimato:** piccolo

### [MEDIO] #3 — Metà delle migration applicate non sono nel repository

- **Tipo:** Incoerenza con i documenti (regola A.5 di `CLAUDE.md`: "una
  migration = un file versionato")
- **Dove:** `supabase/migrations/` (12 file) contro `list_migrations` su
  Supabase (26 migration)
- **Cosa succede:** mancano fra le altre `schema_iniziale`, `rls_policies`,
  `crea_tabelle_obiettivi_target_e_giorni`, `backfill_obiettivi_target_da_obiettivi`,
  `profili_giorni_differenziati`, `grant_authenticated_obiettivi_target_giorni`,
  `pasti_validita`, `fix_search_path_set_updated_at`. Senza queste le policy
  RLS delle 11 tabelle principali non si possono rileggere né ricreare dal
  repository. I file presenti non hanno nemmeno il prefisso di versione
  (`amicizie.sql` invece di `20261015184017_amicizie.sql`), quindi l'ordine
  di applicazione non si ricava dal nome e la CLI di Supabase non li
  riconoscerebbe.
- **In parole semplici:** è come avere in produzione delle tabelle create con
  DDL eseguito a mano, senza il sorgente in libreria. Funziona finché il
  sistema c'è. Se devi ricostruirlo, non sai più com'era fatto.
- **Perché conta:** §10.4 ricorda che il progetto gratuito è già stato messo
  in pausa una volta. Ricostruire un database da zero, o dimostrare che la RLS
  è giusta, oggi dipende solo dal server.
- **Come sistemarlo:** il testo di ogni migration applicata è nella colonna
  `statements` di `supabase_migrations.schema_migrations`. Una query in sola
  lettura lo recupera. Si salvano i 26 file come
  `supabase/migrations/<version>_<name>.sql` e si rinominano i 12 esistenti
  con il loro prefisso. Nessuna modifica al database.
- **Impegno stimato:** piccolo

### [MEDIO] #4 — Nessun "Esporta i miei dati" né backup: un anno di diario dipende da un progetto gratuito

- **Tipo:** Rischio (perdita di dati) / previsto e mancante
- **Dove:** §10.4 di `PUNTO_DI_PARTENZA.md`; §11 "Non ancora costruito"
- **Cosa succede:** §10.4 indica due difese: la copia IndexedDB e un pulsante
  "Esporta i miei dati". La prima c'è, la seconda no. La copia locale non è un
  backup: "Esci" la svuota (§9.6), e Safari su iOS può cancellare i dati di
  un sito che non apri da tempo.
- **In parole semplici:** il SAVLIB della tua libreria dati non è mai stato
  schedulato.
- **Perché conta:** con 390 voci e 3 utenti reali il diario sta già
  accumulando storia che non si ricostruisce.
- **Come sistemarlo:** un pulsante in Impostazioni che legge da Dexie le 11
  tabelle dell'utente e scarica un JSON (`Blob` + link di download). Zero
  costi, nessuna modifica allo schema. Riduce anche un rischio di privacy:
  i dati sono tuoi e te li porti via.
- **Impegno stimato:** piccolo/medio

### [MEDIO] #5 — Funzioni fuori dall'MVP costruite prima dei rimedi e delle fasi previste

- **Tipo:** Incoerenza con i documenti (ordine di sviluppo, §6)
- **Dove:** §6 e §11 di `PUNTO_DI_PARTENZA.md`
- **Cosa succede:** l'ordine dichiarato è 0-1-2 → settimana d'uso vero → 3
  (recenti, preferiti, pasti salvati) → 4 Open Food Facts → 5 OCR →
  6 Statistiche. Fatto e in produzione: 0-3, più Amici, condivisione
  alimenti, foto profilo, onboarding, animazione di apertura, cambio nome e
  icona. Non fatto:
  - **catalogo precaricato** (§10.1, che il documento chiama "il rischio più
    serio per il posizionamento");
  - **Esporta** (#4);
  - fasi 4, 5 e 6;
  - la "settimana d'uso vero" (Prossimi passi, punto 5), ancora aperta.

  Amici e foto profilo sono eccezioni decise e scritte (§9.5, §3), quindi non
  sono "abusive". Ma la foto profilo non riduce l'attrito dell'inserimento, e
  allarga la superficie di privacy (un bucket Storage, una tabella in più, 4
  policy, una funzione `security definer`).
- **In parole semplici:** il criterio di §1 dice di chiedersi, per ogni
  funzione, se rende più facile registrare un pasto. Le ultime tre settimane
  di lavoro sono andate soprattutto su cose che non lo fanno.
- **Perché conta:** un utente nuovo (un amico appena invitato) trova ancora
  il catalogo vuoto, cioè il massimo attrito proprio quando decide se l'app
  gli piace.
- **Come sistemarlo:** prima di nuove funzioni sociali o estetiche:
  catalogo precaricato (un JSON di 150-200 alimenti che popola Dexie al primo
  avvio, §10.1), poi Esporta, poi Statistiche.
- **Impegno stimato:** medio (è una scelta di priorità, non una correzione)

### [BASSO] #6 — Password minima di 6 caratteri e controllo delle password compromesse spento

- **Tipo:** Rischio (sicurezza)
- **Dove:** `src/lib/actions/auth.ts:52`; advisor Supabase
  `auth_leaked_password_protection`
- **Cosa succede:** `if (password.length < 6)` è l'unico requisito, ed è
  anche il minimo predefinito di Supabase. Il controllo su HaveIBeenPwned è
  disattivato. Per quanto ne so è disponibile solo dai piani a pagamento:
  verifica sulla dashboard prima di decidere.
- **Perché conta:** poco con la beta a inviti, di più il giorno in cui l'app
  si apre (§9.6).
- **Come sistemarlo:** lunghezza minima 8 su Supabase (Authentication →
  Providers → Email → minimum password length, gratuito) e lo stesso numero
  in `registrati` e in Cambia password. Se il controllo HIBP è davvero a
  pagamento, aggiungere l'avviso fra quelli accettati in §9.6, così non si
  ridiscute a ogni `get_advisors`.
- **Impegno stimato:** piccolo

### [BASSO] #9 — Policy di `giorni` e `obiettivi_target` sul ruolo `public` invece di `authenticated`

- **Tipo:** Incoerenza (innocua)
- **Dove:** `pg_policies`: le 8 policy di `giorni` e `obiettivi_target` hanno

- **Cosa succede:** per un visitatore anonimo `auth.uid()` è null e

  `alter policy … to authenticated` (additivo, nessun dato toccato). Non
  merita un deploy da solo.

### [MIGLIORIA] #10 — La policy degli username si regge sulla RLS di `amicizie`

- **Dove:** `supabase/migrations/amicizie.sql:145-153`
- **Cosa succede:**
  ```sql
  or exists (select 1 from public.amicizie a
             where a.user_id = nomi_utente.user_id
                or a.amico_id = nomi_utente.user_id)
  ```
  L'`exists` non nomina `auth.uid()`. È giusto solo perché la sottoquery
  passa dalla RLS di `amicizie`, che mostra solo le righe in cui sei una delle
  due parti. È voluto (§9.6, "una riga di amicizie che può vedere"). Ma se un
  giorno quella policy si allargasse, per esempio per un'altra funzione, gli
  username di tutti diventerebbero leggibili senza che nessuno tocchi
  `nomi_utente`.
- **Come sistemarlo:** rendere esplicito il legame:
  `… where (a.user_id = (select auth.uid()) and a.amico_id = nomi_utente.user_id)
  or (a.amico_id = (select auth.uid()) and a.user_id = nomi_utente.user_id)`,
  con gli stessi filtri su stato e `deleted_at`. "Per costruzione, non per
  attenzione" (§9.6).
- **Impegno stimato:** piccolo (una migration additiva + le prove già scritte)

### [MIGLIORIA] #11 — Le foreign key permettono di puntare a righe di un altro utente

- **Dove:** `voci_diario`, `preferiti`, `composizioni_voci` → `alimenti`;
  `obiettivi_target` → `obiettivi`; `voci_diario` → `pasti`
- **Cosa succede:** il controllo di una foreign key in Postgres ignora la
  RLS. Un utente può quindi scrivere una riga sua che punta all'`id` di un
  alimento privato di un altro, e gli id degli alimenti di un amico sono
  visibili in `alimenti_condivisi.alimento_origine_id`. Non esce nessun dato
  (ho controllato: 0 righe incrociate oggi) e le cancellazioni sono logiche.
  Resta però un'incoerenza possibile, e un modo di sapere se un id esiste.
- **Come sistemarlo:** non urgente. Se un giorno l'app si apre, servono
  foreign key composte `(alimento_id, user_id)`, oppure un trigger che
  controlli lo stesso `user_id`.
- **Impegno stimato:** medio

## Cose fatte bene (e verificate)

- **RLS:** attiva su tutte le 15 tabelle di `public`, ogni tabella dati con le
  4 policy `user_id = (select auth.uid())`. `alimenti`: lettura delle righe
  condivise (`user_id is null`) per tutti, scrittura solo sulle proprie e non
  verificate, quindi nessuno può riscrivere il catalogo condiviso (§10.8
  rispettato). Bucket `foto-profilo` privato, solo JPEG, 500 KB, percorso
  vincolato alla propria cartella.
- **Funzioni `security definer`:** tutte con `search_path = ''`, controllo
  di `auth.uid()` in testa, esiti a codice invece di dati altrui, lock
  espliciti contro le corse (`for update`, `pg_advisory_xact_lock`). Le
  funzioni dei trigger non sono eseguibili da `anon`/`authenticated`.
- **Chiavi:** nel client solo URL e chiave publishable. `CODICE_INVITO` solo
  lato server, e ricontrollato dal trigger su `auth.users` con il segreto nel
  Vault: chi chiama `signUp` direttamente con la chiave pubblica viene
  rifiutato lo stesso. `.env*` in `.gitignore`. Nessuna `service_role` nel
  codice.
- **Il giorno:** `oggiLocale` usa l'orologio locale. L'aritmetica dei giorni
  parte dal mezzogiorno (niente salti col cambio d'ora), e i test girano con
  `TZ=Europe/Rome` fisso, così il caso 00:30 si prova davvero. Gli unici
  `toISOString()` sono istanti (`updated_at`, `creato_il`), mai date del
  diario.
- **Giorni passati:** la voce prende la data del giorno mostrato,
  `consumato_alle` resta vuoto fuori da oggi, il limite oggi + 7 è
  ricontrollato nel repository (`dataScrivibile`) e non solo nella pagina, e il
  tipo di giorno si scrive alla prima voce ("la trappola" di §3).
- **Calcoli:** `totaleVoce` = valore per 100 g × `quantita_g / 100`, sulla
  copia dei valori salvata nella voce. Arrotondamento solo in
  visualizzazione. Grammi e valori validati nel client e da 51 `CHECK` sul
  database.
- **Medie:** non esistono ancora (Statistiche è un segnaposto), quindi
  nessun bug. Quando arriveranno, la regola "solo giorni con voci, futuri
  esclusi" è già scritta, e `eFuturo` è pronto. Manca il test n. 2 di §10.5.
- **PWA:** nessuna pagina viene renderizzata dal server con dati
  dell'utente (sono tutte client), quindi la cache delle pagine non può
  mostrare dati di un altro. "Esci" svuota Dexie e cache con il contatore
  `epoca` contro i salvataggi in ritardo.
- **Sync:** `updated_at` lo riscrive il trigger del server (§10.6 rispettato),
  ordine genitori → figli, voci di altri utenti mai inviate con la sessione
  sbagliata, voci irrecuperabili accantonate invece che perse.
